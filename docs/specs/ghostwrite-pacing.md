# 代笔节奏与防水：卷规划、批次骨架、写后判水

> 状态：P1–P5 已实现（2026-10-07），待真机验证。待定问题已按最小方案裁决，见“已裁决”。
> 依据：《赵大来了》第 1–57 章回溯标注实验（见文末“实验证据”）。

## Problem Statement

作者用代笔模式连写多章时，剧情会“水”：章章都办完一件事，但局面没往前走；或者同一种变化换个道具反复上演（52《搓绳》、53《扣舌断了》、54《半日工》都是“赵大无声送物、沈砚默默收下”）。

原因不在写手，而在规划结构：

1. **只有逐章的贪心规划，没有整批的方向。** 代笔每章入口只拿“下一章计划”。批内第 2～N 章的计划由审稿步骤顺手拟定并自动确认，拟定时不知道这一批一共几章、最后要走到哪，只能选局部最稳妥的“把这件事办完”。
2. **没有更上层的节奏账。** 二三十章尺度上，主线该在什么时候到达下一个里程碑，没有任何记录。主线暂时没有“下一件大事”时（第 39 章以后），系统察觉不到，代笔就只能在关系戏和公事里打转。
3. **验收只看“事件发生了没有”，不看“局面变没变、是不是新的”。** 孤立打分会高估重复变化：52–54 每章关系轴都能拿 2 分。
4. **伏笔抽取了却没进规划。** 每章同步时会抽取伏笔（埋下/推进/回收），但拟计划时看不到“还没结的线”；写稿上下文里的“未回收伏笔”段只读 Android 导入的文件，iOS 原生项目里永远为空。

作者要的不是“每章都急着推主线”，而是张弛有度、但**不水**：慢章可以，只要每章都有新东西；长高潮可以，不设上限。

## Solution

在现有“本章计划 → 写稿 → 审稿收录 → 同步”流水线之上加三层：

1. **卷规划（新建，分支级）**：卷目标 + 4–6 个主线里程碑 + 节奏账。作者给方向或交给 Agent 判断，两种方式都由作者确认。“往后几章”备注保留不动，继续承载作者对近几章的具体意图。
2. **批次骨架（每批一次）**：开批前从卷规划的当前位置推导整批路线——起点状态、终点状态，每章一行（状态变化、代价、推进/回收哪条线、节奏位、强度、预计字数、结尾钩子）。骨架经独立评审打分，不过就带理由重写，最多 3 轮；作者只确认这一次骨架，不再逐章确认计划。
3. **写后判水（每章）**：每篇候选在审稿收录前，带着最近 5 章的“主要变化”做两次独立判断；任一遍新意分 ≤1 即判水，打回改写，并告诉写手重复了哪一章的什么。同时按喘息预算检查：连续低强度章总字数不得超过 8000 字。

每章的判断结果写进**节奏账**，既用于下一章的比对，也用于卷规划的进度判断（落后/超前）。

## User Stories

### 卷规划

1. 作为作者，我想在讨论里说一句方向（“这卷让他在军中立住脚”），让 Agent 据此提出完整卷规划，以便我不用自己拆里程碑。
2. 作为作者，我想完全交给 Agent，根据总纲和已写内容自行提出下一卷规划，以便我只做确认。
3. 作为作者，我想在确认前看到卷目标、每个里程碑及其大致章节位置，以便判断节奏是否合我意。
4. 作为作者，我想随时改写或替换卷规划，以便故事方向变了时不必推倒重来。
5. 作为作者，我想看到当前进度（到了第几个里程碑、用了多少章/字、落后还是超前），以便知道主线是否在推进。
6. 作为作者，我希望主线迟迟没有下一个里程碑可推进时，系统主动停下来问我，而不是让代笔自己填空。
7. 作为作者，我希望“往后几章”备注保持原样可用，并在近期安排上优先于卷规划。
8. 作为作者，我希望“往后几章”和卷规划进度要求冲突时，系统停下来问我，而不是自行裁决。

### 批次骨架

9. 作为作者，我想在开一批代笔前看到整批骨架，以便一次确认整批走向。
10. 作为作者，我想让 10 章的骨架比 5 章的更丰富（多一个小弧或中点反转、多一条副线），而不是把同样的剧情拉长。
11. 作为作者，我想看到骨架每一行写明“这章结束时谁的处境变了、付出了什么代价”，以便一眼看出有没有空转的章。
12. 作为作者，我想看到骨架的评审分数和扣分理由，以便判断要不要改。
13. 作为作者，我希望骨架过不了硬门槛时系统自动重写，最多 3 轮仍不过时交给我决定，不空转。
14. 作为作者，我想直接改骨架里的某一行再确认，以便加入自己的想法。
15. 作为作者，确认骨架后我希望整批连写，不再逐章确认计划。
16. 作为作者，我希望每章的本章计划都从骨架对应行和真实写出的上一章推导，以便既守方向又接得上。
17. 作为作者，我希望某章实际落点偏离骨架时，剩余章节自动重排而终点状态不变（处理方式见“待定问题”）。
18. 作为作者，我希望骨架能看到还没结的伏笔，并安排推进或回收其中一些。

### 写后判水

19. 作为作者，我希望每章写完后自动判断“是不是水”，以便水章不进正文。
20. 作为作者，我希望判水时对照最近 5 章的主要变化，以便换道具的重复也能被认出来。
21. 作为作者，我希望慢章只要有一条轴出现新变化就不算水，以便保留张弛。
22. 作为作者，我希望判为水的章自动改写，改写说明里写明“重复了第几章的什么”。
23. 作为作者，我希望自动改写有次数上限和空转熔断，复用现有的改写预算。
24. 作为作者，我希望连续低强度章（喘息段）总字数不超过 8000 字，超了就要求下一章抬升强度。
25. 作为作者，我希望连续两章都是“例行公事办完、局面照旧”时被打回。
26. 作为作者，我不希望系统限制高潮段的长度。
27. 作为作者，我想在暂停卡片上看到判水理由（新意分、重复了哪章），以便决定改写还是人工润修。

### 节奏账与回溯

28. 作为作者，我希望每章收录后自动记下它的五轴变化、强度、节奏位、主要变化、字数，以便后续比对和看进度。
29. 作为作者，我想对已经写好的书做一次回溯标注，以便老项目也能接上判水和进度账。
30. 作为作者，我希望回溯标注前告诉我要调用多少次模型，以便控制花费。
31. 作为作者，我希望改写或回退某章后，节奏账里对应记录随之失效重算，以便账和正文一致。
32. 作为作者，我想看一条全书节奏曲线（五轴合计 + 字数 + 喘息段），以便直观感受张弛（可后置）。

### 兼容与可靠性

33. 作为作者，我希望老项目升级后照常打开，新记录缺失时按“无卷规划”运行。
34. 作为作者，我希望单章节数（批量 1）的代笔照常可用，不强制骨架。
35. 作为作者，我希望判水调用失败属于基建失败，不把候选判死，继续时从当前阶段重试。
36. 作为作者，我希望导出/导入工作区时卷规划、骨架、节奏账都能往返保留。

## Implementation Decisions

### 领域模型（全部分支级，宿主是唯一写入者）

- **卷规划记录**：卷目标、里程碑列表（文本、预计章节位置、状态：待达成 / 已达成 / 已改道、达成于哪章）、来源（作者方向原文 / Agent 自拟）、状态（草稿 / 已确认）、内容摘要哈希。每分支同时只有一份生效。里程碑状态只由宿主根据节奏账推进，模型只提议。
- **批次骨架记录**：所依据的卷规划哈希、目标章数、起点状态、终点状态、逐章行、评审结果（各维度分数、扣分理由、轮次）、状态（草稿 / 已确认 / 已完成 / 已作废）。逐章行字段：
  - 状态变化（章末谁的处境与上章不同）
  - 代价
  - 线索动作（推进或回收哪条未结线）
  - 节奏位（铺垫 / 升级 / 高潮 / 余波）
  - 强度（1–5）
  - 预计字数
  - 结尾钩子
- **节奏账条目**（每章一条）：章节 ID、所依据的章节版本 ID、字数、五轴（事件 / 关系 / 认知 / 内心 / 蓄势，各 0–3 分加一句“变了什么”）、强度、节奏位、主要变化（≤40 字）、是否例行公事、两遍新意分、重复引用（章号 + 重复了什么）、判水结论、来源（代笔 / 回溯 / 手写同步）。章节版本 ID 与当前正文不符即视为过期。
- “往后几章”记录不改动。
- 新记录全部可选，缺失时文档按旧行为解析；导出/导入工作区时以新的 Markdown 节点往返。

### 节奏规则（纯函数，单一策略模块）

- **判水**：同一候选独立判两遍，`water = min(新意分A, 新意分B) ≤ 1`。新意分：0=无新变化，1=细微，2=明确，3=重大不可逆。
- **例行公事门槛**：节奏账最近一章与当前候选都被判为例行公事 → 判水。
- **喘息段**：两遍平均强度 ≤2 的连续章。喘息预算 = 8000 字（按实际字数累计，不按章数）。候选使当前喘息段累计超过 8000 字 → 不通过，改写说明要求抬升强度或推进事件轴。
- **骨架硬门槛**（宿主能算的由宿主算）：
  - 每行都有非空的状态变化
  - 按预计字数与强度计算，骨架内任一喘息段不超过 8000 字
  - 终点状态不同于起点状态
  - 不重演最近 5 章的主要变化
  - 相邻两行的状态变化不得是同一类（这一项交给评审模型判断）
- **骨架规模随章数伸缩**（写进拟定提示词）：
  - 5 章：一个小弧，1 个主要转折
  - 10 章：两个小弧或一次中点反转，外加一条批内回收的副线
  - 每章至少 1 个不可逆的状态变化
- **不设高强度连续上限。**

### 模型任务（新增结构化任务，沿用现有结构化执行器、重试与超时策略）

1. **卷规划拟定**：输入总纲、写作要求、当前状态、节奏账尾部、未结线索、作者方向（可空）。输出卷目标和里程碑。
2. **批次骨架拟定**：输入已确认卷规划及当前进度、节奏账最近 5 章的主要变化、未结线索、“往后几章”、目标章数。上一轮评审的扣分理由（如有）一并带入。
3. **骨架评审**：独立一次调用，不与拟定同一次。输出硬门槛逐项结论和五维分数（推进幅度、代价/风险、新信息、冲突升级、旧线处理），并附扣分理由。阈值暂定：硬门槛全过，且任一维度不低于 2。
4. **章节节奏判定**（即判水，同一候选并发两次）：输入候选全文、上一章结尾约 600 字、最近 5 章的主要变化、本章骨架行。输出五轴、强度、节奏位、主要变化、是否例行公事、新意分、重复引用、是否落实骨架行。这一个任务同时产出节奏账条目，回溯标注也复用它。

所有新提示词遵守版本纪律：当前版本号随改动递增，旧版本号必须保留在兼容列表中，否则历史回执会让老项目打不开。

### 流水线改动

- **开批**：批量 >1 且分支有已确认卷规划时，先拟骨架，走评审迭代，然后暂停等作者确认。这一步取代“确认首章计划”。批量 =1，或分支没有卷规划时，走现有路径。
- **每章入口**：本章计划由“骨架对应行 + 真实上一章”拟定。骨架行的状态变化和代价写成计划“必发生”的第一条，现有验收因此会卡住它。批内计划继续自动确认。
- **审稿收录之前**：插入判水，两次调用并发。判为水时生成失败回执（新暂停原因“无新变化”，允许自动改写，继续时必须重写），重复引用写进改写说明。改写预算和相同指纹熔断复用现有机制。判水调用本身失败时归为基建失败，不判死候选。
- **收录之后**：把判水结果写入节奏账。宿主根据“是否落实骨架行”和里程碑命中，推进里程碑状态和进度账。
- **偏离**：候选未落实骨架行但已通过判水并收录时，剩余骨架行需要重排，终点状态不变。重排后是自动继续还是暂停问作者，见“待定问题”。
- **主线缺位**：卷规划没有待达成的里程碑，或骨架拟定判断无法推进下一个里程碑时，暂停并提示作者补方向。

### 未结线索

把分支状态上的伏笔事件按线索名折叠成“还没结的线”：埋下、推进、重开都算未结，回收则移除，保留最新一条摘要。这份列表注入卷规划拟定、骨架拟定、本章计划拟定，以及写稿上下文中的“未回收伏笔”段（与 Android 导入文件合并）。已有一个未完成的起步改动和两条守护测试，尚未运行。

## Testing Decisions

好测试只测外部行为：给定文档或节奏账输入，断言规则判定、注入内容、流水线停在哪个阶段、写了哪些记录；不断言内部调用顺序和私有结构。

测试缝，由高到低，尽量复用现有的：

1. **流水线缝**：会话视图模型 + 脚本化模型适配器，跑完整代笔批次，断言暂停原因、阶段、收录章数和节奏账条目。先例：会话视图模型测试中的批次代笔用例。
   - 必测场景：
     - 骨架评审不过时重写，3 轮后交给作者
     - 判水命中时自动改写，改写说明带重复引用
     - 喘息超限时打回
     - 判水调用失败归为基建失败
     - 批量 1 和无卷规划时走旧路径
2. **创作服务缝**：创作服务的拟定/评审/判定入口 + 脚本化适配器，断言结构化输出解析、失败时的处理（不确认、不落盘）和落盘结果。先例：下一章计划拟定并确认的用例。
3. **纯策略缝**：节奏规则模块。用回溯实验数据做表驱动测试：给定第 39–57 章的两遍新意分，判水结果必须是 41、42、43、49、50、51、53、54；给定实际字数和强度，喘息段必须只有 49–55 超限（16363 字）。先例：代笔改写策略的纯函数测试。
4. **持久化缝**：归约器命令、文档校验、工作区导出导入往返。先例：“往后几章”的归约器测试与工作区备份测试。

修复类改动沿用红→绿：先写失败的守护测试，再改代码。提示词改动要同时更新提示词目录快照测试和版本兼容测试。

## Out of Scope

- 高强度连续上限（作者明确不要）。
- Android 端对等实现。
- 逐章由作者确认计划（骨架确认后批内自动）。
- 改动“往后几章”的数据结构和语义。
- 节奏曲线的 App 内可视化（用户故事 32 可后置，先用导出数据 + 外部图表）。
- 文风层面的复读，比如收口句式重复（本轮未选）。

## Further Notes

### 已裁决（原待定问题，按最小方案）

1. 偏离骨架：剩余章节自动重排并继续，不暂停；重排后的骨架仍须过评审，3 轮不过才暂停。
2. 判水与评审模型：沿用创作模型策略，不新增设置。
3. 回溯标注：不做全书回溯；判水时若最近 5 章缺节奏账条目，按需单遍补标。
4. 骨架评审阈值：硬门槛全过且五维每项 ≥2。
5. 存储归属（实施时调整）：
   - 卷规划存为**项目级**自定义资料（类型名「卷规划」，注入关闭），复用资料的版本、导出导入与编辑；作者保存即确认，宿主达成里程碑时改写这份资料。暂不做分支隔离（分支各自的进度会共用一份）。
   - 节奏账是可重算的派生数据，存独立缓存文件 `pacing-ledger/{projectID}.json`（按章节版本 ID 作键，版本不符即失效）。
   - 批次骨架是单批运行状态，存进代笔进度 sidecar。
   - 骨架行通过「本章计划拟定 / 审稿顺带拟下一章」两条路径的上下文注入（`BATCH SKELETON LINE FOR THIS CHAPTER`），不新增计划字段。
   - 判水开关：`NovelSessionViewModel(chapterPacingChecksEnabled:)`，正式 App 打开，测试替身默认关。
   - 骨架待确认复用现有「已拟定 · 待确认」暂停状态（planProposedForNewBatch），续跑即确认。
6. 骨架逐行编辑不做（用户故事 14 后置）：作者可改卷规划或“往后几章”后重新生成骨架。
7. 卷规划由代笔设置页生成和编辑（方向可空 = 交给 Agent）；不新增讨论工具。

### 实施阶段（按序推进，每阶段完成后做独立审查）

1. **P1 未结线索**：伏笔事件折叠成未结线，注入本章计划拟定与写稿上下文的“未回收伏笔”段。
